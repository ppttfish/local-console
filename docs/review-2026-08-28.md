## 一、最严重：同一进程里跑了好几套后台任务

Electron GUI 启动一次，下面这些实例会被**各创建一份并在后台各自循环**：

| 实例 | 创建位置 | 数量（GUI 模式） |
|---|---|---|
| `UsageScanner`（30s 全盘扫 jsonl） | `plugins/builtin/token-usage/index.ts:38`（plugin onLoad）<br>`ipc/index.ts:205`<br>`http-server.ts:76` | **3** |
| `SubscriptionRefresher`（5min 拉配额） | `token-usage/index.ts:39`<br>`ipc/index.ts:38,202`<br>`http-server.ts:77` | **3** |
| `PortScanner`（2s netstat + PowerShell） | `main/index.ts:243`<br>`http-server.ts:74` | **2** |
| `ServiceManager` | `main/index.ts:241`<br>`http-server.ts:73` | **2** |
| `LogStreamer` | `index.ts:243` / `http-server.ts:75` / 每个 `ServiceManager` 构造里各 1 个（`service-manager.ts:76`） | **4** |

外加 `startMcpSubprocess()`（`main/index.ts:286`）又在**独立进程**里开了第 4 个 `UsageScanner` + 第 3 个 `PortScanner`（`mcp/standalone.ts:39,43`）。

后果：

- **CPU/IO 翻 3~4 倍**：每个 scanner 都 `readFileSync` 整个 `~/.claude/projects/**` 等目录（`scanner.ts:126`），dsh 还要 `zstdDecompress` 整文件（`parsers.ts:228`）。
- **订阅 API 被调用 3 次**：用户视角是"我加了 1 个订阅，5 分钟被请求 3 次"，容易触发 provider 限流。
- **两个 `ServiceManager` 状态不互通**：在 9600 Web 端启动的服务，桌面端 `procs` Map 里没有，GUI 显示"已停止"，反之亦然。`svc.delete()` 也只会停一半。
- **数据库被初始化两次**：`main/index.ts:252` 和 `http-server.ts:65` 各调一次 `initDatabase()`，后者直接覆盖模块级 `db` 变量，前一个连接泄漏且永不 `close()`（`db.ts:70-79`）。

修复方向：把 `Runtime` 做成单例（`http-server.ts` 已有的 `runtime` 对象正好可以复用），`startHttpServer` 接受注入而不是自己 new；`ipc/index.ts` 与插件共用同一个 scanner 实例。

## 二、`[P0]` 进程守护：Job Object 大概率杀掉了第一个服务

`utils/proc-tree.ts:98-119`：

```ts
let jobStarted = false
export async function ensureJobObjectForPid(pid: number) {
  if (jobStarted) return true            // ← 只有第一个 pid 会被 attach
  ...spawn powershell → CreateAndAssign(pid) → Write-Output "ok"
}
```

两个问题叠加：

1. **`jobStarted` 一旦为 true 就永久短路**，第 2 个及以后的服务根本没被纳管（退出时会残留孤儿进程）。
2. 脚本里设了 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`（`proc-tree.ts:81`），而 Job 句柄**只存在于那个一次性 PowerShell 进程里**。PowerShell 退出 → 最后一个句柄关闭 → Job 销毁 → **被 assign 的服务进程被内核杀掉**。Node 侧没有保存任何句柄（`jobProc` 只是 `ChildProcess`，不是 HANDLE）。
   即"第一个启动的服务可能在 1~3 秒内（PowerShell + Add-Type 编译 C# 的时间）被干掉"。
   另外 `Write-Output "ok"` 无条件执行，`CreateAndAssign` 内部抛异常也会返回成功。

建议：要么删掉这段（退化成"退出时 `taskkill /t`"，`stopAll()` 已经能做），要么用 `koffi`/`node-gyp-build` 直调 kernel32 把句柄留在主进程里。至少要把 `jobStarted` 改成 per-pid、给 PowerShell 加 timeout、并检查 `CreateAndAssign` 的返回值。

## 三、`[P0]` 日志链路：同步 I/O + 每 2 秒全量重读

1. **写**：`service-manager.ts:382-403` 每收到一个 stdout chunk 就 `appendFileSync` + `statSync`。高频输出的服务（vite / tail 编译）会持续阻塞主进程事件循环。
   达到 2MB 时还要 `readFileSync` 整个文件再 `writeFileSync` 截断（`:388-391`），一次同步读写 1~2MB。
   → 改成 `createWriteStream`（append 模式）+ 在内存里累计字节数（去掉 `statSync`），截断改成"超过阈值就 `close` + `rename` + 新建"，由流自己背压。

2. **读**：`log-streamer.ts:34` 的 `tail(id, n)` **完全忽略 `n`**（`:35 void n`），只要文件 < 2MB 就 `readFileSync` 全文。也就是 UI 上那个"最近 100 / 300 / 1000 行"是假的 —— 选 100 行照样传 2MB 字符串过 IPC。
   而 `Logs.vue:51` 每 2 秒 `refresh()` 一次，于是：**每 2 秒主进程同步读 2MB → 序列化 → 渲染端 `split('\n')` → 整体替换 `lines.value` → 重渲染 1000 个 div**。
   → `tail` 用 `openSync` + 从文件尾往回读块，拼到够 N 行为止；主进程侧缓存文件 size/mtime，没变就直接返回 `{ unchanged: true }`；渲染端做增量追加而不是整体替换。

3. **实时推送是死代码**：`preload/index.ts:76-86` 暴露了 `onStateChanged` / `onServiceLog`，但主进程**从没发过**这两个事件（全仓 `webContents.send` 只有 updater 一处）。事件总线 `emit_event` 也只在本进程内广播，没人往渲染端转发。所以才退化成 2s 轮询。
   → 在 `registerIpcHandlers` 里订阅 `bus`，节流后 `win.webContents.send(IpcChannels.EventStateChanged, state)`，轮询间隔可以从 2s 放宽到 10s 甚至去掉。

## 四、`[P1]` 端口扫描：每 2 秒 netstat，PID 一变就全量 WMI

`port-scanner.ts`：

- `netstat -ano -p TCP` 每 2 秒 spawn 一次（`:45`），×2 实例 = 每秒一次。
- PID 集合**只要有一个变化**就 `Get-CimInstance Win32_Process` 全量枚举再 `Where-Object` 过滤（`:137`）。这是 O(机器总进程数) 的操作，按注释约 1.5s，×2 实例。
- `emit_event({type:'port:changed'})` 把整份端口表推给总线（无人消费），同时 `StateGet` 每次都带上全量 `ports`（`ipc/index.ts:108`）。

优化：
- 降到 5s 间隔，且只在窗口可见/GUI 在前台时跑（隐藏到托盘就暂停）。
- `Get-CimInstance` 换成按 PID 过滤的 CIM 查询（`Get-CimInstance -Filter "ProcessId=1 or ProcessId=2 ..."`），或者干脆用 `wmic`（`proc-info.ts` 里已有的 `pidSnapshot` 批量实现）复用，别两套。
- 缓存 key 从"全部 PID 拼接"改成"新出现的 PID 集合"，只对新增 PID 补查。
- 用 `Set<number>` 存 pids，`pidKey` 拼接字符串在几百个 PID 时本身也不便宜。

## 五、`[P1]` SQLite / 查询层

- **每次查询都 `prepare()`**：`storage.ts` / `db.ts` 里所有函数都是 `getDb().prepare(sql).run(...)`。better-sqlite3 没有语句缓存，等于每次都重新编译 SQL。加一个 `Map<string, Statement>` 缓存即可（注意 `initDatabase` 重建 db 时清空缓存）。
- **重复写 cursor / 全删全写**：`scanner.ts:170` 和 `:217` 在 opencode.db 或任一 dsh 文件变化时 `DELETE FROM agent_usage WHERE agent = ?` 再全量插回。3 个 scanner 实例同时干这件事，会互相踩。
- **`listSessions` 相关子查询**（`storage.ts:320-322`）：`GROUP BY session_id` 后每行再跑一次 `(SELECT model ... ORDER BY at DESC LIMIT 1)`。加索引 `(session_id, at)` 或改成窗口函数 `ROW_NUMBER() OVER (PARTITION BY session_id ORDER BY at DESC)`。
- **`readOpenCodeDb` 双 LIKE 全表扫**（`parsers.ts:328`）：`data LIKE '%assistant%' AND data LIKE '%tokens%'`，`data` 是长 JSON，每次 opencode.db 的 mtime 变化就全表扫一遍。改成按 `time_created > last_cursor` 增量 + 在 JS 里过滤 role。
- 缺 `agent_usage(at)` 之外的组合索引：筛选常用 `agent + from`，已有 `idx_usage_agent_at(agent, at)` 是对的；但 `by_day`/`timeline` 的 `strftime` 分组没法走索引，数据量大时会全扫。可考虑物化一张 `usage_daily` 汇总表。

## 六、`[P1]` 渲染端：2 秒一次的无差别重渲染

`App.vue:18` 每 2 秒 `store.refresh()` → `applyState` 把 `services.value` / `ports.value` **整体换成新数组新对象**。连带影响：

- `Launchpad` 所有 `ServiceCard` 的 props 引用变化 → 全部重渲染（每张卡有十几个 computed + 一个 `Motion` 组件 + `Sparkline`）。
- `Monitor.vue:32` 的 `top` computed 每轮都 `[...store.ports].sort()` 再 slice(50)，50 行表格整体 diff。
- 数据其实 99% 的时间没变。

优化：`applyState` 里做浅比较（`id` 相同且关键字段相同就复用旧对象），或者在 `ServiceManager.list()` 返回前对比上一份快照。另外 `Logs.vue` / `Usage.vue` 的轮询在路由离开时已清理，但 `App.vue` 的全局轮询在切到设置页时没必要还拉全量 state。

## 十一、`[P0]` 增量游标按行号走，文件被重写就永久丢数据

### 现象

同一份代码、同一台机器，常驻实例（累积了几周的 `state.db`，增量扫描）与全新库（对当前文件一次性全量解析）口径不一致。以「今天 + ZCode」为例：

| 口径 | 常驻实例 | 全新库（全量） |
|---|---|---|
| 行数 | 206 | 344 |
| tokens | 3294 万 | 1.42 亿 |

### 根因

`scanner.ts` 对 `~/.zcode/cli/rollout/model-io-*.jsonl` 按**行号**做增量：游标记"已读到第 N 行"，下次只解析第 N 行之后的内容。这隐含假设文件只追加不改动。

但 ZCode 的 model-io 文件（单行可达 300KB，存的是完整模型 I/O）会被**压缩重写**：行数变少、内容重排。一旦发生，`Math.min(cursor.lines_seen, lines.length)` 会把 `startFrom` 直接顶到文件末尾，重写窗口里的用量**永远**不会被解析，游标还越滚越远。

线上数据实测（`state.db` 快照，2026-08-28 16:39）：

```
model-io-sess_9b035973-....jsonl  游标 8 行  -> 文件 7 行  (2.1 MB)  压缩
model-io-sess_b7d8ff38-....jsonl  游标 17 行 -> 文件 16 行 (3.7 MB)  压缩
model-io-sess_29732b38-....jsonl  游标 33 行 -> 文件 32 行 (9.2 MB)  压缩
18 个 zcode 游标里 3 个处于「游标越过文件末尾」状态
agent_usage 现有 zcode 行：894 行 / 2.017 亿 tokens
```

这也解释了"数字不涨了"的体感：扫描每 30 秒还在跑、数字有微涨，但每次压缩都会永久抹掉一段，再也追不回真实值。

### 修复

1. **游标加前缀指纹**：`agent_file_cursor` 新增 `head_hash`。扫描时若发现
   - 文件行数 < 游标行数（被压缩），或
   - 已入库前缀的指纹与记录不符（内容被改写），
   则对该文件走**全删全写**。
2. **删除边界用 `source_file`**：`agent_usage` 新增 `source_file` 列 + 索引。
   不用 `session_id` 做边界，因为 zcode 的 session_id 取自行内字段（`e['sessionId']`），
   按它删会漏行。老数据 `source_file` 为 `NULL`，删除时附带
   `agent + session_id` 兜底；实测线上 17 个 zcode session_id **全部**能与文件名派生值对应，
   兜底是精确的，不会漏也不会多删。
3. 指纹只取「前缀行数 + 前缀字符总数 + 首行头 128 字符哈希 + 末行尾 128 字符哈希」，
   O(n) 累加长度而不做全量摘要 —— zcode 单文件可达数十 MB，每 30 秒都要扫一次。

### 升级路径（无需手动重扫）

迁移只做加列 + 加索引，不动现有数据。升级后**第一次扫描**就会命中
「文件行数 < 游标行数」，自动对那 3 个文件做全删全写，丢失的用量会自己补回来。

唯一遗留：升级前写入的行 `source_file` 为 `NULL`，只能靠兜底规则回收。
扫描器统计里暴露了 `legacy_rows`，用量页会在大于 0 时提示点一次「重新扫描」把兜底换成精确删除。
（该提示与手动重扫的既有代价一致：源文件已删除的旧会话会从总量里消失。）

### 验证方式

把线上 `state.db`（含 `-wal` / `-shm`）复制到临时目录，在副本上跑迁移并比对游标与真实文件行数，
线上库未被修改。

## 建议动手顺序

1. **进程守护**（第二节）—— 可能正在实际杀死用户服务，先验证再决定删还是修。
2. **合并重复实例**（第一节）—— 一步到位省掉一半以上的后台 CPU。
3. **日志写路径改流 + tail 真正按行数读**（第三节）—— 高频日志服务下主进程卡顿的直接原因。
4. **接通事件推送，把 2s 轮询降下来**（第三节末 + 第六节）。
5. **拆包 / 路由懒加载**（第八节）—— 首屏收益明显。
6. 其余按表清理。

### 第三轮验证：去掉 cache 重复算

用户拿 ZCode 平台「使用统计」页（今日 1.1 亿、5.3-Flash 1.06 亿、5-Turbo 423 万）
做基准，scanner 报 2.16 亿，差一倍。

根因：API 的 `input_tokens` 包含 cacheRead（同一请求的"读"是从缓存命中，
仍占 input 配额），`cached_tokens` 单独字段只是记"其中缓存"。我之前 SUM
`input + output + cached` 把 cache 算了第二遍，5.3-Flash 缓存命中率高所以偏差巨大。

修 `storage.ts` 7 处 SUM 公式 + `total_tokens` JS 计算 + 接口注释：
- `SUM(input_tokens + output_tokens)` —— zcode / openai / anthropic 平台口径
- `cost_usd` 不动：cache 价格不同（cache_read 0.1x、cache_write 5x），必须含
- `cached_tokens` 字段保留展示（缓存命中量），`cache_hit_ratio` 公式待下次再校

实测新口径：今日 zcode 109,776,677 tokens / $132.16，与平台 1.1 亿完全一致，
模型分布 5.3-Flash 1.06 亿 + 5-Turbo 423 万也与平台一致。
